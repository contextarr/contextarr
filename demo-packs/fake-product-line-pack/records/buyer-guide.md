# Buyer Guide

## Summary

The fictional buyer guide helps assistants explain which Atlas reference model fits a generic team scenario without using real pricing or availability claims.

## Fit Signals

| Signal | Suggested Model |
|---|---|
| Simple setup and narrow scope | Atlas Mini |
| Balanced features and repeatable workflows | Atlas Core |
| Higher capacity and complex coordination | Atlas Max |
| Unknown requirements | Start with discovery questions |

## Fictional Buyer Segments

| Segment | Best fit | Why |
|---|---|---|
| Solo evaluator with a small pilot | Atlas Mini | Needs a narrow, low-complexity scenario and plain onboarding language. |
| Operations team standardizing repeatable workflows | Atlas Core | Needs balanced capability, clearer support boundaries, and reusable guidance. |
| Cross-functional program group with heavier coordination | Atlas Max | Needs capacity framing, dependency tracking, and a careful expectation-setting brief. |
| Buyer asking for guarantees or unlisted integrations | Discovery first | Requirements are unclear and should not become promises. |

Support should ask about workflow size, review burden, and compatibility expectations. It should avoid real pricing, real availability, compliance claims, support response guarantees, and future-feature commitments.

## Notes

All model names, fit signals, and positioning are invented for public Contextarr demos.
